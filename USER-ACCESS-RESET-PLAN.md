# School user access reset from the Users table

Status: **implementation added; connected acceptance pending** (2026-09-21). Source and package changes need separate Git, deployment, database, and browser evidence before this journey is called accepted.

Reference: Kafil's `USER-ACCESS-RESET-PLAN.md` and its shipped `najm-auth@4.0.8` recovery contracts. School must implement the same **one admin action, server-selected consequence, stale-confirmation refusal, truthful delivery, and value-free audit** pattern, adapted to School's account model. Do not copy Kafil's role/profile mapping or assume its tests prove School.

## Product contract

Add one **Reset access** action to the admin Users table and its card presentation. The confirmation explains the consequence for the selected account and requires an administrative reason. The request contains only `{ reason, expectedMode }` plus the user ID in the route. `expectedMode` confirms what the dialog explained; it never selects a workflow. The server reloads the account and relevant School profiles, resolves the mode, and returns `409` with no mail, credential change, or success audit if the account changed or the confirmation no longer matches.

| Current account, after fresh server lookup | Server-selected mode | Result |
| --- | --- | --- |
| Active parent, matching parent profile, valid stored Moroccan CIN | `parent_credential_setup` | Replace the credential with normalized CIN through Najm, durably require password setup, revoke sessions. Parent signs in with email + CIN, completes `/change-password`, then signs in with the new password. |
| Active student, teacher, or login-enabled staff account with its matching profile | `reset_email_sent` | Send a one-time password reset to the account's **current** email. Revoke prior sessions when the password is saved, as Najm defines. |
| Pending invited parent, student, teacher, or login-enabled staff account with its matching profile | `invitation_resent` | Resend the existing account's invitation. Do not create another user or profile. |
| Active direct Users-page account with no School profile | `reset_email_sent` **only after** the Phase 0 account-origin and role-policy gate is satisfied | Send to the current account email. |
| Pending direct Users-page invite with no School profile | `invitation_resent` **only after** the Phase 0 invite-provenance gate is satisfied | Resend to that existing invited account. |
| Inactive, self, bootstrap/admin target, role/profile mismatch, orphaned teacher/staff link, unknown role, or unproven pending account | Unsupported | Refuse safely; do not reactivate or repair it as a side effect. |

Parent CIN is nullable in School. An active parent with absent or invalid CIN is **ineligible** for the CIN path and receives a safe conflict; do not silently switch to email after the dialog promised a CIN reset. Student code, birth date, teacher/staff CIN, and arbitrary profile data are **not** temporary credentials in this slice. A pending parent uses invitation resend, never CIN. A teacher's `teachers.staffId -> staff.userId` chain must resolve to the same target user; a staff HR row without a login (`userId` null or no mapped access role) is not a target. Treat the user's auth status separately from HR/student status and define the exact eligible status combinations in server tests.

No credential, CIN, token, link, or email body appears in the dialog, API response, audit metadata, logs, or test evidence. Existing public forgot-password, invite consumption, and password-change routes remain the downstream flows.

## Phase 2 — one admin-only School command

1. Add a School-owned `POST /api/admin/access/users/:userId/reset-access` controller/service/repository slice under `packages/server/src/modules/`, registered through the existing module barrel. 2. In the service, reload user status, role, current email and linked profile IDs at execution time. Reject actor == target and bootstrap/admin targets; do not trust the row's role, email, status, CIN, or selected mode. Compare `expectedMode` with the mode resolved from freshly loaded state before any mutation or send. Return a safe `409` on stale/unsupported state; never let an operator-shaped claim or client-supplied mode steer a parent into mail.
3. For an eligible parent, use a narrow server-side query by `userId` to read the parent's CIN. Validate it with Najm's Moroccan CIN helper, then pass it directly to `resetToTemporaryCredential`. Include the School audit write in the same transaction if the package's transaction boundary supports it; prove rollback and session invalidation semantics in a real PostgreSQL test. If a shared transaction cannot encompass both, document the exact partial-failure recovery and stop before declaring the path complete.
4. For email modes, call the Najm method **by user ID**, outside the audit transaction, and record the actual result afterward. Return a discriminated response such as `{ userId, mode, delivery: 'sent' | 'simulated' | 'not_sent' | 'not_applicable' }`. Distinguish console/memory acceptance from real transport using the resolved provider, and show `not_sent` as failure requiring retry. If Najm reports `undeliveredLinkLive`, add only that value-free key to audit and log the anomaly at error level; a compare-and-delete returning `false` after a newer mint is not a cleanup failure. 6. ## Rollback and completion

- Before any reset is executed, disable/revert the School endpoint and UI and return to a compatible package pin only after checking the lockfile and patch. Preserve the audit trail.
- After a CIN reset, the old password and revoked sessions cannot be restored safely; the parent must finish credential setup or receive a newly reviewed recovery. Sent links remain subject to Najm's one-time/expiry rules; removing the button cannot unsend mail.
- Complete only when the eligibility matrix (including the direct Users-page account decision), stale-confirmation refusal, truthful delivery and token cleanup reporting, privacy-safe audit, source/database gates, and connected journeys have evidence. Record unsupported account classes and any remaining acceptance/deployment work explicitly.
